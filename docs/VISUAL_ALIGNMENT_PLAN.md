# AGV 3D 场景原型对齐改造建议

> 文档日期：2026-09-03  
> 对比基准：`docs/prototypes/agv-3d-scene-prototype.png`  
> 当前实现：仓库当前 HEAD，Mock 数据源默认 60 台车辆  
> 文档性质：视觉与技术改造建议，不包含代码修改

## 1. 结论

当前项目的工程骨架已经比较完整，相机、配色、雾、阴影、节点 LOD、车辆标签、独占区、交通锁等优化也已经生效。现在与原型图的主要差距不再是少量颜色或尺寸参数，而是以下结构性问题：

1. 原型图是精心编排的小型展示场景，真实地图是高密度生产拓扑。
2. 当前直接把导航拓扑作为最终视觉地图渲染，缺少独立的展示语义层。
3. 道路、仓储点、节点和标签的几何组织方式，在近景中存在明显的视觉噪声。
4. 车辆、货架、区域发光和场景材质的资产层级仍低于原型图。

如果要求首屏也接近原型图，需要引入“全厂总览 / 作业区 / 车辆近景”三级视觉层级，而不能始终把全厂所有对象等权显示。

## 2. 当前项目实现概况

项目使用 React 19、React Three Fiber 和 Three.js 构建单 Canvas AGV 数字孪生监控场景。

- `src/app/App.tsx` 负责运行时配置、地图加载、数据源选择、Canvas 和 WebGL 恢复。
- `src/app/scene/AgvMonitorScene.tsx` 组合地图、车辆、相机和渲染质量等 Feature。
- `features/map-visualization` 负责地坪、道路、节点、仓储点、充电桩、停车点和独占区。
- `features/fleet-monitoring` 负责车辆实例、状态标签、选中/告警环和交通锁。
- `features/camera-navigation` 负责自动取景、轨道控制和车辆跟随。
- `features/render-quality` 负责自动质量降级和 DPR、阴影、标签等能力切换。
- Mock 和 WebSocket 共用统一的归一化车辆事件模型。

现有功能分层和高频数据不进入 React State 的设计是合理的，视觉改造应继续保持现有 Feature 边界，不需要推翻整体架构。

## 3. 原型图与真实数据的客观差异

| 项目 | 原型图 | 当前真实地图 |
|---|---:|---:|
| 节点 | 约 20 个 | 4,291 个 |
| 仓储表现 | 约 4 组货架 | 1,185 个仓储站点 |
| 充电桩 | 约 3 个 | 59 个 |
| 车辆 | 约 8 台 | Mock 默认 60 台 |
| 地图形态 | 连续、紧凑的小路网 | 4 个分离连通区域，跨度约 239m × 126m |

由此产生两个互斥目标：

- 如果必须在首屏完整展示全厂，构图不可能与原型图一样紧凑。
- 如果必须让首屏接近原型图，就需要默认聚焦一个活跃作业区，把完整全厂总览作为二级视图。

仅调整 FOV、亮度或节点尺寸，无法消除数据密度和空间分布造成的差异。

## 4. 目前已经完成、无需重复实施的工作

当前代码已经完成以下视觉基础：

- 相机 FOV 已降至 25°，形成较弱的透视效果。
- 自动取景已经从包围球改为基于视口纵横比的地图四角投影包络。
- 地面和背景已经使用灰蓝色阶、渐变背景、暗角和距离雾。
- 道路宽度已经调整为 1.8m，并使用虚线中线。
- 节点尺寸已经缩小，并具有暗色描边和屏幕尺寸 LOD。
- 方向光强度已经降低，阴影已经启用，阴影相机已经按灯光空间地图四角收紧。
- 已使用自定义渐变环境贴图和冷色半球光。
- 车辆已经增加车轮、深色底盘和货物纸箱。
- 车辆标签已经改为深色背景、状态圆点和电量条。
- 独占区已经增加面填充，交通锁已经增加描边和文字。
- 充电桩已经增加闪电贴花、底环脉冲和距离 LOD。
- 停车点已经增加凸起和微光。

后续工作的重点应该从“继续调色”转为“重新组织场景信息”。

## 5. P0：必须优先解决的结构性问题

### 5.1 建立三级场景细节层级

当前项目只有节点、充电桩和标签各自独立的淡出规则，尚未形成统一的场景细节层级。建议新增独立的场景 LOD 概念：

#### 全厂总览

- 显示区域轮廓、主干道路、车辆/告警聚合和重点标签。
- 隐藏逐个仓储垫、普通导航控制点和非重点车辆标签。
- 独占区和连通区域以块状语义为主，不显示过多内部细节。

#### 作业区视图

- 显示完整道路、精选工位、仓储货架、充电设施、车辆和标签。
- 这是主要对齐原型图的视觉层级。

#### 车辆近景

- 显示车辆全部细节、方向箭头、电量、交通锁和附近节点。
- 可增加更完整的状态文字和局部业务标识。

场景细节等级由相机距离、对象投影尺寸和当前关注区域决定，并应加入迟滞，避免在阈值附近频繁闪烁。

需要注意：场景 LOD 表达的是“当前应该展示什么”，现有 `render-quality` 表达的是“设备性能不足时关闭什么”。两者不应复用同一个状态或等级。

### 5.2 调整默认取景策略

当前 `computeOverviewPose` 会正确地把完整地图装入视口，但四个连通区域之间存在较大空白，因此有效业务对象在首屏中仍然偏小。

推荐方案：

1. 启动后默认聚焦活跃车辆最多的连通区域或配置的默认作业区。
2. 空格键返回完整全厂总览，保留当前交互习惯。
3. 选中或双击车辆后进入局部跟随视图。
4. 可选：出现 L2 告警时只提示，不自动抢占镜头；由产品决定是否支持告警区域定位。

如果产品要求启动时必须完整展示全厂，则应接受首屏不能与原型图构图一致，只能通过区域聚合和语义 LOD 提升可读性。

涉及位置：

- `src/features/camera-navigation/model/overviewFraming.ts`
- `src/features/camera-navigation/hooks/useCameraNavigation.ts`
- `src/app/scene/AgvMonitorScene.tsx`

### 5.3 重建道路连接方式

当前 `buildMapGeometry.ts` 为每条物理路径的起点和终点都生成圆形端帽。真实地图中大量物理路径都只连接相邻节点，因此同一交叉口会叠加多个圆片和条带，形成实际截图中的花瓣、鼓包和交叉纹理。

不应继续通过缩小端帽或压暗颜色掩盖问题，建议从拓扑层处理：

1. 建立物理道路端点邻接关系。
2. 合并经过二度节点的连续道路，生成一条连续 polyline strip。
3. 仅在真实道路末端生成圆形端帽。
4. 每个三岔、四岔或多岔节点只生成一个路口补面。
5. 路口内部不绘制重复虚线中线。
6. 如果需要最高质量，对所有道路中心线生成缓冲多边形并执行平面并集，再统一三角化。

推荐分两步实施：

- 最小方案：连续链合并 + 每个路口只补一次面。
- 最终方案：道路缓冲区多边形并集，彻底消除重叠、缝隙和尖角。

涉及位置：

- `src/features/map-visualization/scene/buildMapGeometry.ts`
- `src/features/map-visualization/model/createMapModel.ts`
- `src/features/map-visualization/components/PhysicalPathsLayer.tsx`

### 5.4 增加地图展示语义层

原始节点类型只描述业务或导航数据，不能直接决定视觉权重。建议在不修改调度数据的前提下，增加派生的 `visualRole`：

- `route-control`：纯导航控制点，监控场景默认隐藏。
- `junction`：需要显示的道路交叉节点。
- `work-station`：真实作业工位。
- `storage-slot`：仓储库位，近景按需显示。
- `charge`：充电设施。
- `park`：停车点。
- `landmark`：独立视觉地标。

生产环境最好由独立视觉配置明确提供角色；基于度数、坐标和节点类型的启发式算法只作为缺少配置时的降级方案。

节点可以继续保持实例化渲染。可在实例数据中增加角色属性，并由 shader 根据场景 LOD 决定显隐，避免逐帧重写全部静态矩阵。

涉及位置：

- `src/features/map-visualization/model/types.ts`
- `src/features/map-visualization/model/createMapModel.ts`
- `src/features/map-visualization/scene/buildMapGeometry.ts`
- `src/features/map-visualization/components/NodesLayer.tsx`
- `src/features/map-visualization/scene/semanticMaterials.ts`

### 5.5 聚合仓储站点

当前 1,185 个 `warehouse` 节点逐点生成方垫。它们实际上更接近库位或取放站点，并不等于 1,185 个独立仓库。直接在每个节点上增加货架会产生更严重的模型海，并遮挡道路。

推荐增加独立的地图视觉配置文件或后端字段，描述：

- 仓储区域 ID 和名称；
- 区域多边形或包围盒；
- 包含的仓储节点；
- 货架行列、朝向和层数；
- 是否显示托盘或纸箱；
- 默认镜头区域和重要地标。

配置存在时按显式数据生成货架；配置缺失时，可以按节点共线关系、间距和方向做聚类，但聚类结果必须允许人工覆盖。

渲染建议：

- 全厂总览只显示仓储区域色块或轮廓。
- 作业区视图显示货架整体轮廓。
- 车辆近景才显示单个库位标识、托盘和纸箱。
- 货架、立柱、横梁、托盘和纸箱分别使用少量 InstancedMesh，不为每个货架创建独立组件。

涉及位置：

- `src/features/map-visualization/scene/buildLandmarkData.ts`
- `src/features/map-visualization/components/LandmarksLayer.tsx`
- 建议新增 `warehouseVisualModel.ts` 和 `WarehouseRacksLayer.tsx`

## 6. P1：决定近景完成度的改造

### 6.1 升级车辆模型

当前车辆仍然以基础盒体和箭头棱柱为主。建议使用以下两种路线之一：

#### 路线 A：程序化低模

- 使用倒角盒体或预生成圆角几何改善车壳轮廓。
- 增加独立保险杠、顶盖、车灯和轮毂层次。
- 将固定部件合并进共享几何，控制车辆 Draw Call。
- 保留实例颜色和现有车辆尺寸矩阵。

#### 路线 B：低模 GLB

- 使用一个低面数、单材质或少量材质的 AGV 模型。
- 车壳使用实例颜色或材质变体表达状态。
- 载货与空载使用少量模型变体。
- 避免为每台车克隆独立材质。

如果目标只是接近原型图的卡通工业风，程序化低模已经足够；如果需要品牌车型识别，再选择 GLB。

涉及位置：

- `src/features/fleet-monitoring/scene/createVehicleGeometry.ts`
- `src/features/fleet-monitoring/scene/fleetAppearance.ts`
- `src/features/fleet-monitoring/components/VehicleInstances.tsx`

### 6.2 增加车前方向箭头

原型图中的蓝色箭头是车辆前方独立的地面方向指示，而当前实现主要依赖车体前端的箭头形状。

建议新增一个车辆相关 InstancedMesh：

- 放置在车辆前方约 0.4～0.8m。
- 与车辆方向同步旋转。
- 使用半透明蓝色或按状态着色。
- 根据投影尺寸和场景 LOD 显隐。
- 选中、跟随或重点车辆可以增强亮度。

为避免增加 Draw Call，可以把所有车辆方向箭头合并为一个实例批次。

### 6.3 重构车辆标签内容与避让

当前标签已经具有深色底、状态圆点和电量条，但仍存在以下问题：

- Mock 名称 `mock-agv-0032` 过长，不符合原型中的短编号。
- 状态芯片会挤占名称空间。
- 多台车辆相邻时标签会互相覆盖。
- 标签采用世界尺寸，远近变化幅度较大。

建议改为：

1. 优先显示业务短名，例如 `AGV-032`。
2. 标签基础结构保持“状态圆点 + 车辆 ID + 分段电量条”。
3. 正常状态不显示文字芯片；FAULT、STALE、OFFLINE 等异常状态才显示文字。
4. 标签屏幕尺寸设置上下限，避免近景过大、远景不可读。
5. 在现有逐帧投影循环中增加屏幕空间碰撞网格。
6. 按“选中 > 故障 > 离线/过期 > 低电量 > 普通车辆”排序。
7. 碰撞时隐藏低优先级标签，不移动车辆本体。

屏幕空间碰撞可以使用固定单元格网格，车辆上限 512 台时成本可控，并且仍可通过零缩放隐藏实例，保持现有两层标签 Draw Call。

涉及位置：

- `src/features/fleet-monitoring/hooks/useFleetLabelFrameSync.ts`
- `src/features/fleet-monitoring/scene/labelLod.ts`
- `src/features/fleet-monitoring/scene/labelMaterials.ts`
- `src/features/fleet-monitoring/scene/labelAtlas.ts`
- `src/features/fleet-monitoring/scene/fleetAppearance.ts`

### 6.4 提升道路材质与厚度感

当前道路顶面使用不受光的 `MeshBasicMaterial`，整体较平。原型中的道路更像略高于地面的工业铺装板。

建议：

- 道路增加 3～5cm 深色侧沿。
- 顶面改为受光材质或轻量自定义 shader。
- 使用低金属度、中高粗糙度，保留克制高光。
- 路缘增加窄暗边或顶点色过渡。
- 中线继续采用虚线，但在路口补面区域裁掉。
- 不使用 TubeGeometry，避免对数万条采样段增加无意义几何负担。

### 6.5 改进独占区形状

当前独占区使用成员路径采样点的凸包。在部分区域中，凸包可能覆盖过多内部空地，形成大片蓝色网格区域。

建议优先级：

1. 使用视觉配置或后端提供的显式区域多边形。
2. 对成员道路生成缓冲区并执行并集。
3. 数据缺失时才降级为凸包。

独占区表现建议使用低透明度面填充、HDR 发光边线和贴地名称。名称应根据屏幕尺寸和区域面积显隐，避免在总览中消失、近景中过大。

涉及位置：

- `src/features/map-visualization/scene/buildExclusiveGroupsGeometry.ts`
- `src/features/map-visualization/components/ExclusiveGroupsLayer.tsx`

## 7. P2：视觉质感增强

### 7.1 选择性 Bloom

原型图的充电桩、独占区边缘、交通锁、警示灯和方向箭头具有克制的辉光。当前项目没有后处理链。

不建议直接对整个场景做全局 Bloom，否则车辆标签白字和停车点文字会首先泛光。正确方案是：

- 为允许发光的对象分配独立图层或发光材质标记。
- 仅对充电桩、区域边缘、交通锁、警示灯和方向箭头执行 Bloom。
- 发光对象使用 HDR 强度，普通白字保持 LDR。
- 将后处理资源纳入现有 `contextGeneration` WebGL 恢复链。
- 自动质量降级时允许关闭 Bloom，但不得隐藏告警本体。

### 7.2 地坪细节

当前地坪已经具有低对比网格，但整体仍比较干净。建议增加程序化或小尺寸可平铺纹理：

- 低频明暗噪声；
- 轻微污渍和磨损；
- 不规则细划痕；
- 粗糙度变化；
- 保持对比度较低，不能抢过道路与车辆。

### 7.3 交通锁表现

保持后端上报的真实业务范围，不放大矩形。可以继续增强：

- 半透明悬浮框体或轻微挤出；
- 沿边流动或脉冲；
- 锁定红、申请黄的 HDR 边线；
- 文字根据矩形屏幕尺寸显隐；
- 近景显示文字，总览只保留颜色和轮廓。

### 7.4 阴影策略

当前运行时会出现 Three.js 将已废弃 `PCFSoftShadowMap` 回退为 `PCFShadowMap` 的警告。原型图需要较柔和的阴影，因此应显式选择阴影方案：

- 首先验证 PCFShadowMap 配合收紧后的阴影相机是否足够。
- 若阴影仍过硬，再评估 VSMShadowMap。
- 使用 VSM 时需要测试 light bleeding、额外模糊 Pass 和集成显卡性能。
- 保留车辆假接触阴影，但适当降低透明度，避免与实时阴影双重变暗。

## 8. 图例面板的产品范围冲突

原型图右下角包含路径、节点、充电站、仓库、停车点、独占区和交通锁图例，但当前规格明确排除了 Canvas 外的 DOM 覆盖层。

因此，当前页面没有图例是符合规格的，不是实现遗漏。如果视觉对齐必须包含图例，需要先修改产品规格，再选择实现方式：

- 允许 DOM：使用 DOM HUD，文字最清晰，维护成本最低。
- 仍要求单 Canvas：使用固定在相机前的 WebGL HUD，不随场景透视移动。

图例不应在未修改规格的情况下静默加入。

## 9. 推荐实施阶段

### 第一阶段：信息架构和几何基础

1. 确认默认首屏是完整全厂还是活跃作业区。
2. 建立三级场景 LOD。
3. 增加地图视觉配置和 `visualRole`。
4. 重建道路连续链与路口补面。
5. 仓储点远景隐藏或聚合。

这一阶段完成后，默认总览和图 3 中的近景噪声会明显下降。

### 第二阶段：核心实体表现

1. 生成仓储区域与货架。
2. 升级 AGV 车体模型。
3. 增加车前方向箭头。
4. 简化标签内容并加入碰撞避让。
5. 独占区使用更准确的区域几何。

这一阶段完成后，作业区视图会开始接近原型图的主体观感。

### 第三阶段：材质和后处理

1. 道路增加侧沿和受光材质。
2. 增加选择性 Bloom。
3. 增加地坪粗糙度和磨损细节。
4. 调整交通锁和阴影软化效果。
5. 建立固定截图视觉回归。

## 10. 视觉验收标准

建议使用固定地图、固定 Mock 种子、固定车辆状态和固定相机机位进行截图回归。

### 全厂总览

- 完整地图不被裁切。
- 四个连通区域边界清晰。
- 普通仓储库位和普通节点不形成点阵地毯。
- 只显示选中、故障和关键告警标签。
- 主干道路优先于节点和地标被感知。

### 作业区视图

- 有效作业区域占视口约 75%～90%。
- 同屏普通节点约 20～80 个，不展示全部导航控制点。
- 仓储区域读作货架群，而不是黄色点阵。
- 道路没有花瓣、断头、尖角和重复中线。
- 车辆长度约 45～90px。
- 标签宽度约 80～120px。
- 完整车辆标签约 15～20 个以内，且不得互相覆盖。

### 车辆近景

- 车体方向、车轮、底盘、载货和警示灯清晰可辨。
- 车前方向箭头与车辆朝向一致。
- 标签不遮挡车辆主体。
- 道路边缘、节点描边、交通锁文字和充电桩贴花清晰。
- 受光材质不过曝，状态色保持饱和。

### 性能

- 继续满足 200 台、1080p 场景帧时间 P95 ≤ 40ms。
- 默认画质总 Draw Call ≤ 150。
- 车辆相关 Draw Call 保持现有预算，不通过不断增加 InstancedMesh 堆叠细节。
- 地图静态几何只在加载或地图替换时重建。
- 标签碰撞和 LOD 不引入高频 React State 更新。
- 自动质量降级不能隐藏车辆、物理道路、主状态或 L1/L2 告警。

## 11. 工作量估算

以下是单名熟悉 Three.js 的开发人员完成实现、测试和截图回归的大致量级，不作为固定排期承诺：

| 工作项 | 估算 |
|---|---:|
| 场景分级、默认取景、标签碰撞 | 3～5 个工作日 |
| 道路拓扑与路口重建 | 3～5 个工作日 |
| 仓储区域数据与程序化货架 | 3～6 个工作日 |
| 车辆、方向箭头、Bloom 和材质精修 | 4～7 个工作日 |
| 性能、浏览器和截图回归 | 2～4 个工作日，可与各阶段交叉进行 |

完整做到“既保留真实大地图，又在作业区接近原型图”，合理量级约为 2～4 周。

## 12. 最终优先级建议

最值得优先投入的三项是：

1. **三级场景 LOD**：解决全厂总览与原型化近景之间的目标冲突。
2. **道路拓扑重建**：消除近景中最明显的花瓣、鼓包和交叉纹理。
3. **仓储区域视觉配置**：把 1,185 个离散仓储站点转化为少量可理解的货架区域。

这三项完成后，整体观感才会发生质变。车辆模型、Bloom 和材质精修应建立在它们之上。
